# StyleDNA v2 and scene uniqueness

A SHA-256 signature is derived from NFKC-normalized topic/brief, audience, style, aspect and related visual inputs. Generated fields such as `styleSeed` and `styleSignature` are excluded. The first 32 bits drive the existing palette/backdrop composer; the full `v2-…` signature is saved with the brief. The older `StyleDNA.fromAnswer` seed reader remains available for existing projects.

A scene's signature describes the non-decorative primitive families, quantized positions and sizes. After repair, every candidate is checked against **all** already accepted graphs, including cached and model-designed candidates. The final pass begins with an empty built list, so a model scene cannot collide with itself. Local replanning searches 32 visual families in three layouts (with data-dependent families used only when the beat supplies appropriate input), as well as semantic composer variants. If none passes layout, lint and uniqueness, planning fails explicitly rather than silently accepting a duplicate. Scene-level changes are also gated and model revisions receive rejection feedback. Edited scenes retain their original timeline timestamps.

`pageflip`, `cubeSpin`, `depthWipe`, and `glitchDissolve` are deterministic Canvas transitions; hyphenated spellings are accepted too. Page/cube faces use a perspective mapping, the depth wipe combines a sloped mask with scale, and glitch strip order is seeded from the scene. Both preview and export use the same transition and `RenderPlan`: when adjacent generated code scenes meet, the prior scene's last frame is held beneath the new scene during its entry. This carries the native scene graph, not a frozen copy of separate video/image backdrops; media-backed scenes may therefore need their own media transitions.

The tests exercise normalized identity, five distinct topics, up to 60 unique scenes in four aspect ratios, exhaustion behavior, transition geometry and a seekable prior-frame plan. The repository's Android CI currently treats its unit-test step as non-blocking; an APK workflow success alone does not certify those tests or on-device visual output.
